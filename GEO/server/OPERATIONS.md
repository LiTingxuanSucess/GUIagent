# 生产服务恢复与重启

生产机以 root 执行（普通账号加 `sudo`）：

```bash
/root/workspace/GUIAgent/GEO/server/restart.sh
```

脚本重启 `geo-server` 与 `geo-monitor`，直接使用已部署二进制。原有 `start.sh` 会重新编译并安装 service，适用于部署；日常恢复使用 `restart.sh`。

重启前使用现有部署屏障暂缓新任务执行，最多等待 300 秒让已有 queued/running 任务完成。新到任务保持 queued，重启后按原 ID 加载继续执行。已有任务未完成、任务记录损坏、其他部署持有屏障或服务目录不匹配时退出，错误会打印到终端。脚本不会强杀业务任务；已有任务长期等待时先排查对应任务和账号状态。

重启后最多等待 180 秒，检查两个 systemd 服务、HTTP/HTTPS 登录页、AK/SK 签名的只读站点接口以及重启后新生成的健康监控快照；HTTPS 使用本地服务证书验证，不提交真实问题。成功后更新 `geo-server.pid`。正常结束、启动失败或收到终止信号时会清理本次部署屏障；并发执行会退出。SIGKILL/断电无法运行清理，此时先确认没有其他部署，再检查 `data/.deployment-drain.json`；屏障有有效期，脚本不会自动覆盖其他部署屏障。

可调整等待时间：

```bash
./restart.sh --wait-seconds 600 --health-timeout 240
```

排查状态与日志：

```bash
systemctl status geo-server geo-monitor --no-pager
journalctl -u geo-server -u geo-monitor -n 80 --no-pager
tail -n 80 /root/workspace/GUIAgent/GEO/server/geo-server.out.log
```

公网入口：<https://YOUR_GEO_HOST:8443/>。服务页面和只读接口就绪不代表六个平台的登录、验证码或真实问答均可用，具体情况在后台和任务详情查看。

## 额度与账号限制

看板顶部新增“额度与账号限制”，默认显示尚未确认恢复的账号，支持查看已恢复记录。首次发现与最近发现来自实际网页尝试；历史记录回填会标注来源。平台给出的恢复时间与系统最早复查时间分列；未知恢复时间不显示倒计时或承诺自动恢复。只有网页实际成功才确认恢复，登录成功或 API 兜底成功不会清除网页限制。

旧版账号停用状态在启动时自动迁移，保留原停用时间及原页面所属任务。未知重置日期默认按 30 / 60 / 120 分钟退避；明确的禁言截止、重置日期或次月 1 日零点按平台提示处理。到期只允许后续任务复查，不主动发送测试问题。到期前的额度 / 禁言限制不调用 CLI 修复。

更新前可对已完成任务做隔离迁移检查：

```bash
python3 scripts/verify_account_limits.py --binary bin/geo-server.quota-optimize.new
```

该检查复制终态任务和账号元数据到私有临时目录，禁用浏览器与真实提问，验证两次启动的限制记录一致及历史任务未改写；若源数据有未完成任务会退出。短信回调绑定原发码页面及轮次，接续阶段单独保存在 `data/sms-handoffs.json`。提交期间发生中断会转为“结果未知”人工待办，不自动重放验证码。未知 / 丢失的原页面同样需要检查；不会通过重新打开登录页或重复发码来掩盖接续失败。

## 各平台网页请求成功率

模块内六张平台卡片分别提供“网页优先”开关。开启时该平台先网页、失败后 API；关闭时该平台直接调用 API，不影响其他平台。例如 DeepSeek 网页不可用时，只关闭 DeepSeek 的开关，豆包等平台仍按各自设置执行。升级时六个平台继承旧总开关的状态，切换保存后无需重启。新提交任务逐平台保存策略，同一任务可混合网页优先与直接 API；已受理任务及其重试继续按原策略执行，历史记录和已有原页面续跑不受切换影响。状态文件为 `data/jobs/request-routing/state.json`。读取或保存失败会在模块内显示，结果不明时重新读取服务端状态，不自动重复写入。管理接口更新使用 `site_id` 限定平台；不传该字段的旧版写入仍会统一设置全部平台。

看板渠道总览下方的“各平台网页请求成功率”用六张卡片分别展示豆包、DeepSeek、Kimi、千问、文心一言、元宝的网页成功率、成功 / 失败次数及跳过 / 历史未知次数，跟随所选日期和统计范围更新。成功率按网页成功次数除以网页成功与失败次数之和计算，包含换号及重试，API 兜底不改变网页失败记录；无明确结果时显示“—”。点击卡片中的“查看失败请求”会筛选该平台的网页失败明细。

## Cursor CLI 分析与人工处理

看板 `/admin/monitor` 顶部“当前待处理”按当前启用账号和平台去重，区分人工处理与自动处理 / 短信等待。已有任务或自动恢复占用的页面会标为自动处理中；处理入口直接打开对应账号和平台，不自动发码或启动 CLI。历史调用中的“转交短信 / 人工”不计为当前待办。

“Cursor CLI 逐次调用分析”按选定日期和筛选条件展示每次调用，包含账号登录检测和手动辅助，支持导出全部筛选结果。页面复核成功、原网页续跑成功和业务任务最终成功分别列示，不把 API 补齐算为 CLI 修复成功。

离线逐条关联分析可运行：

```bash
python3 scripts/analyze_cursor_calls.py --date 2026-10-20 --output-dir data/cursor-review-20261020
```

导出只含脱敏账号和结构化证据，不包含验证码、完整手机号码或 CLI 原始对话。短信相同账号 / 平台 / 时间窗口的关联不等于填码成功；后台应确认对应号码确实接入回调，而不是复用其他号码收到的验证码。
