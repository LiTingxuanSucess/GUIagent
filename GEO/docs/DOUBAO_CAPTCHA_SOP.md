**豆包提问验证：人工接管步骤和经验，2026-10-15**

给人看的是前面的操作说明。给 AI 看的是后半段，按状态、页面元素和手势写，不靠截图印象。两边都只处理本机浏览器里已经弹出的豆包语义验证。登录短信另走「登录状态」，不要混用。

# 给人

## 先分清两个入口

后台左侧有两个模块：

| 模块 | 什么时候出现 | 你要做什么 |
| --- | --- | --- |
| 登录状态 | 账号掉线、要发短信、登录页上的点选或滑块 | 发码、填短信，或在截图上点登录验证 |
| 回答验证 | 豆包已经登录，一提问就弹出语义验证 | 在当前对话页上把图拖进框里，再提交 |

回答验证的文案一般是「平台触发安全验证」或「语义安全验证」。状态是 `need_captcha`。这种行不要在登录状态里当短信登录处理。

当前任务会等待网页恢复。完成验证后，服务端在原账号、原标签上独立复核，再按私有 journal 提取已有回答或继续原任务；CLI 不新发或重复发送问题。只有真实恢复失败或账号不可用时，编排器才决定后续账号或官方接口。

豆包被标成提问验证时，服务同步调用本机 Cursor 命令行按后半段处理当前页，同一账号同时只跑一个，并持有账号租约。自动恢复、复核和续跑期间，人工可查看截图，点击和拖动会被独占保护拒绝。由 GEO_CURSOR_WEB_RECOVERY 开关启用；未配置时兼容 GEO_CURSOR_CAPTCHA_AGENT=1。

## 什么时候去点

提问触发验证后，本机浏览器会停在当时那条豆包对话上，大约保留 20 分钟。打开 `https://YOUR_GEO_HOST:8443/admin`，强制刷新，进「回答验证」。

只点时间最新的那一条「接管验证」。更早的行多半页面已经没了，点开会落到豆包首页，右边写成「已登录，不用发短信」。那不是验证码还在。

接管之后，左侧必须还是验证弹层，而不是「有什么我能帮你的吗？」。如果已经是普通聊天首页，这条验证作废，不要在首页上乱点。

## 怎么点这一题

豆包这道题不是点一下就过。弹层上会有一句要求，例如「在公园能看到的事物或动物」，下面是九张图，再下面是「拖拽到这里」和「提交」。

按这个顺序做：

1. 看清上面那句要求。
2. 把每一张符合要求的图，从图片上按住，拖到「拖拽到这里」，松手。
3. 拖成功后，这张图会出现蓝框，框上的数字会加一，例如变成「2」。图还留在九宫格里，这是正常的。
4. 符合要求的图都拖完后，再点「提交」。
5. 弹层消失后，点右边的「重新检测」。状态应变成「已登录：登录有效」，这一行从回答验证里消失。

只在图片上点一下，只会选中或没有拖进去，框上的数字不会增加，提交也不会过。已经拖进去的图不要再拖一次。选中后的图上有关闭层，再点容易把选中取消。

滑块是另一种登录验证：在截图上按住滑块，拖到缺口，松手，再点「重新检测」。不要把语义题当成滑块。

## 弹层上的字怎么读

- 框上的数字等于已经拖进去的张数。数字还是 0，就还没拖成功。
- 「验证超时，请根据提示重新操作」表示这一题作废。页面会换成新题目，上一题选中的图不算数。看新的那句话，重新拖。
- 右边如果还显示「发短信验证码」「填验证码」，说明这页被当成登录流程了。语义题不要点发送短信。
- 「已登录，这个页面可以直接使用」只在截图已经是正常聊天时出现。这时没有验证可点。

## 今天实际走过的一次

## 不要做的事

- 不要为了赶时间连点同一张图。先确认数字加了，再拖下一张。
- 不要在验证还在时点「重新检测」或刷新整页。检测可以，但刷新或新开首页会把这题弄丢。
- 不要把回答验证里的旧行逐条点开试。页面不在的行会变成已登录首页。
- 不要在这道题上发短信。短信只属于登录状态。
- 验证层消失后如果对话里暂时没有回答，CLI 也不要新发问题；由服务端读取原任务 journal，确认尚未发送、生成中或回答完成，再续跑或提取。

# 给 AI

目标：通过调用提供的 CDP 连接唯一指定 target，在当前豆包标签上完成语义验证，确认验证层消失后只输出 recovery-candidate。不要使用后台 check/click/drag 接口：本次租约会阻止这些接口。不要新开首页、发送短信、改指纹、改代码、重启或自行重发问题；由服务端独立复核并续跑原任务。

## 先判断是不是这道题

同时满足才继续：

- 站点是 `doubao`。
- 调用提供当前任务、账号、CDP、唯一 target_id 和私有 journal 路径，且当前连接的就是该 target。
- 给定标签的地址属于 `https://www.doubao.com/chat/`，可以是 `local_...` 或具体对话地址，并且页面里确有 `rmc.bytedance.com/verifycenter/captcha/v2` 这个 iframe。
- 后台保存的 `need_captcha`、`logged_in` 等状态只作参考，不是操作前提：服务端可能先调用恢复，随后才写失败状态。以给定 target 的实际验证层为准，不根据旧列表挑另一个页面。

下面任一情况停止点击和拖动，并按所见交回服务端：

- 给定 target 已是普通聊天，没有验证 iframe，也没有登录提示：输出 recovery-candidate；不要发新问题验证。
- 右侧或状态被写成「已登录：登录有效」，给定 target 中确实没有验证 iframe 或登录提示：只输出 recovery-candidate，仍由服务端独立复核。
- 文案是登录短信，例如「已点击发送，请在截图上完成安全验证」「等待你填写短信验证码」：输出 recovery-stopped: sms_required。那是登录状态，不是回答验证。

注意：人在截图上点过一次之后，服务端 `Refresh` 会把说明改成「请在截图上点击验证码」。这句话不再包含「语义」或「平台触发安全验证」，回答验证列表会把它漏掉。以验证 iframe 还在不在为准，不要只看这句文案。

`GEO_DOUBAO_BACKEND=agentbay` 的含义是豆包先走本机 Chrome，失败后才允许 AgentBay。这次提问的诊断字段是 `browser_backend=local`。接管对象是本机那个 Chrome 标签。

验证页大约保留 20 分钟。这个保留只在标记文案含「语义安全验证」或「平台触发安全验证」时生效。超过保留时间后浏览器会被关掉，再打开就是新首页。

## 页面里认哪些元素

验证在 iframe 里，文档标题是「验证码」。外层豆包页面的正文里没有「拖拽到这里」。

| 元素 | 选择器 | 含义 |
| --- | --- | --- |
| 九张图 | `.canvas-container` | 每张是一个 canvas。中心点用来起拖 |
| 已拖入 | `.canvas-container.selected` | 已经算进框里 |
| 关闭层 | `.close-container` | 铺满已选中的那一张。再在这张上按下会取消，不要拖它 |
| 投放框 | `.drag-area` | 松手必须落在这里。框里的第一行数字是已拖入张数 |
| 拖影 | `.drager` | 拖动过程中的影子。没出现不代表失败，以数字增加为准 |
| 提交 | `.vc-captcha-verify-pc-button` | 全部拖完再点。未选够时 class 里会有 `disable` |

题目是验证文档正文的第一行，例如「哪些东西需要用电力驱动」。每次拖之前重新读这一行。出现「验证超时，请根据提示重新操作」时，旧选择作废，下一行就是新题目。

## 手势

对每一张还没选中、且符合当前题目的图，做一次完整拖动：

1. 在该张 `.canvas-container` 的中心按下左键。
2. 按键保持按下，把指针移到 `.drag-area` 的中心。移动过程中 `buttons` 必须仍是左键按下。中途松开只会变成一次点击，数字不会加。
3. 在投放框内松开。
4. 再读 `.canvas-container` 的选中情况和 `.drag-area` 的数字。

成功的判定是数字比拖之前大 1，并且这张带上 `selected`。图仍留在九宫格里，这是正常的。

不要拖已经 `selected` 的图。后台截图接口的单次拖动如果在选中图上起手，按下点会落在 `.close-container` 上，数字不变。下一张必须从未选中的图中心起手。

全部符合的图都让数字加上之后，再点「提交」。这个按钮的 `getBoundingClientRect()` 可能是 `0,0` 的 50×30，那个矩形不是屏幕上的按钮。提交按钮画在验证弹层右下角。点完后验证 iframe 的执行上下文会销毁，这是提交生效的迹象，不是脚本写坏了。

CLI 必须通过给定 CDP/target 顺序拖动。这道题有时限，每张图单独一轮会拖到超时换题，所以看完验证截图、确定全部符合的未选中图后，用一条命令依次拖完：`drags 'X1,Y1,X2,Y2;X1,Y1,X2,Y2' --frame verifycenter`，起点是各张 `.canvas-container` 中心，终点是 `.drag-area` 中心，坐标取 iframe 内 `getBoundingClientRect`。工具内部每张之间会停顿并按住左键完整拖动，返回里的 `frame_text` 带有框上的数字。数字等于这次拖的张数才点提交；少了就重读选中情况，只对仍未 `selected` 的符合图逐张补拖。不要用后台 POST .../drag、check 或 Refresh 接口：本次持有租约，人工写操作被独占保护。不要并行拖、刷新或另开首页。验证页还在时必须沿用给定标签。

## 做完之后查什么

按这个顺序确认，都成立才算接管完成：

1. 框架树里不再有 `verifycenter/captcha`。
2. 保持给定 target 和原会话。已有完整回答时记录实际会话地址；尚未生成时不要求 `/chat/local_...` 已变成对话号，由服务端按 journal 继续判断。
3. CLI 通过给定 CDP/target 观察没有登录提示、没有验证码后，输出 recovery-candidate 并交回。
4. 服务端在仍持有租约时独立探测同一 target，确认登录有效后继续原任务。CLI 不调用后台 check 接口，也不把自己的退出码当复核结果。

2026-10-15 16:43 那次，账号 `acct_836d3b506d1b`（尾号 8568）的结果地址是 `https://www.doubao.com/chat/38447333137471234`。对话里能看到杭州的回答。第一题「在公园能看到的事物或动物」超时作废；第二题「哪些东西需要用电力驱动」拖入两台电梯，数字为 2，提交后验证层关闭。

验证通过后，服务端根据同一任务的私有 journal 继续原网页流程：已有回答就提取，已发送仍生成就等待，确认未发送才由服务端发送原问题。CLI 始终不发送问题。历史记录可能保留早期网页失败和接口答案，不据此猜测本次是否已发送。

## 停手条件

- 页面已无验证 iframe，且没有登录提示：输出 `recovery-candidate`，交服务端独立复核，不能当成失败统一交人。
- 连续两次拖动数字都未增加，或新题无法确认：输出 `recovery-stopped: no_progress`。
- 给定 target 已消失：输出 `recovery-stopped: target_missing`，不转到其他标签或账号。
- 需要短信：输出 `recovery-stopped: sms_required`，由已有服务端回调/人工登录流程接续；不自行发码。
- 需要另一个手机号、另一个页面或超出本次语义验证的登录操作：输出 `recovery-stopped: operator_required`。

只输出对应的一行 marker。题目、数字和地址如需保留，只记私有诊断，不改用其他浏览器通道，不新发问题。
