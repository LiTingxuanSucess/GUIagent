# APAgent 生产化架构设计说明

日期：2026-05-24

## 背景

APAgent 面向代购商的自动下单场景，目标是提升下单效率，减少人工反复填写客户信息和支付信息，同时降低真实卡号、个人信息在外包开发或运营流程中泄露的风险。

系统可能处理真实的：

- 收货人姓名
- 联系方式
- 收货地址
- 支付卡信息
- 平台账号和登录态

因此生产化设计必须优先考虑安全、审计、权限和稳定性，而不是只追求自动化速度。

## 核心结论

APAgent 可以做高并发自动下单，但不应把“频繁换 IP 绕风控”作为核心方案。

动态 IP 或代理基础设施可以用于合法合理的用途，例如：

- 网络出口隔离
- 区域出口
- 故障切换
- 不同客户组的网络隔离
- 出口容量扩展

但不应把它设计成规避平台风控、规避封禁、绕验证码、绕反欺诈或伪装大量不同真实用户的工具。

如果业务量达到上百并发，优先路线应该是：

- 争取官方 API、企业采购或 reseller 通道
- 支付信息 token 化
- 稳定、可审计的网络出口
- 任务队列和 worker 池
- 明确的并发控制
- 人工确认和接管能力
- 必要时申请平台白名单或企业采购支持

## 安全原则

真实卡号和个人信息是最高风险数据。系统设计上要默认：

- 开发人员不应该接触完整卡号和 CVV
- 普通运营不应该看到完整卡号和 CVV
- 日志、截图、浏览器 trace 不应该保存敏感字段
- 自动化脚本只在任务执行期间短时间使用敏感数据

### 支付信息处理

不建议在 SQLite、PostgreSQL 或普通业务表中明文保存完整卡号。

推荐做法：

- 使用 PCI 合规的支付 vault 或支付服务做 token 化
- 业务库只保存：
  - payment token
  - 卡尾号
  - 有效期
  - 持卡人标签
  - 所属信息套件 ID
- CVV 不长期保存
- 如果网页下单必须填写卡号和 CVV：
  - 只在任务执行时临时解密或拉取
  - 只保存在内存中
  - 执行完立即清理
  - 严禁写入日志、截图、浏览器 trace、前端响应和普通数据库字段

### 人工信息权限

人工信息应分权限查看和操作。

建议：

- 普通运营只能选择信息套件，不能查看完整卡号
- 管理员也只显示卡尾号
- 编辑信息时，卡号和 CVV 留空表示保留原值
- 每次敏感信息读取都记录审计日志

审计内容至少包括：

- 操作人
- 任务 ID
- 信息套件 ID
- 操作时间
- 操作原因
- 使用的 worker

### 密钥和加密

不要把加密密钥写在代码、配置文件或数据库里。

可选方案：

- 本地部署：Windows DPAPI
- 云部署：云厂商 KMS
- 多节点部署：HashiCorp Vault 或同类密钥系统

密钥需要支持：

- 权限控制
- 访问审计
- 轮换
- 紧急吊销

## 推荐生产架构

```text
APAgent Web 后台
  |
  | HTTP API
  v
FastAPI 后端
  |
  | 创建任务 / 查询状态
  v
任务队列
  |
  | 分发任务
  v
Worker 池
  |
  | 浏览器自动化
  v
电商平台 / Apple Checkout

PostgreSQL：业务数据、任务状态、审计日志
Vault/KMS：支付敏感数据
Redis/队列系统：待执行任务
```

## Web 后台设计

客户使用的后台应该是标准管理系统风格，不展示内部自动化细节。

页面模式：

- 左侧导航
- 表格列表
- 页面右上角新建按钮
- 新建/编辑使用弹窗表单
- 行内操作：编辑、删除、执行
- 下单任务和执行进度放在同一个页面

不应该在客户界面展示：

- CDP 地址
- Cloak 描述
- 浏览器 profile 路径
- 内部调试路径
- 自动化实现细节

## 后端 API

生产后端至少需要：

- SKU 管理
- 人工信息管理
- 平台管理
- 账号管理
- 下单任务管理
- 任务执行
- 任务进度查询
- 审计日志查询
- worker 状态查询
- 网络出口配置

基础 CRUD：

- `GET/POST/PUT/DELETE /api/skus`
- `GET/POST/PUT/DELETE /api/identities`
- `GET/POST/PUT/DELETE /api/tasks`
- `POST /api/tasks/{id}/run`
- `GET /api/tasks/{id}`

## 任务队列

FastAPI 的 `BackgroundTasks` 只适合 demo，不适合上百并发生产任务。

生产环境建议使用任务队列：

- Redis + RQ
- Celery
- Dramatiq
- Arq
- 其他可靠队列系统

任务队列需要支持：

- 全局并发限制
- 平台级并发限制
- 账号级并发限制
- 卡级并发限制
- 地址级并发限制
- 出口级并发限制
- 重试
- 取消
- 超时
- 死信队列
- 失败分类

## Worker 池

Worker 是实际执行浏览器自动化的进程。

建议：

- 一个 worker 只跑有限数量的浏览器上下文
- 一个账号或客户组绑定独立浏览器 profile
- 登录态和任务隔离
- worker 崩溃不影响任务状态一致性
- 每个阶段都写回任务日志
- 支持人工接管

不要让一个 FastAPI 进程直接扛上百个浏览器任务。

## 任务状态机

任务状态必须清晰，不要只用几个松散字符串。

推荐状态：

```text
created          已创建
queued           已排队
browser_ready    浏览器就绪
product_opened   商品页已打开
sku_selected     SKU 已选择
bag_added        已加入购物袋
checkout_started 已进入结账
shipping_filled  收货信息已填写
payment_filled   支付信息已填写
review_ready     到达最终确认页
submitted        已提交订单
blocked_manual   等待人工处理
failed           执行失败
cancelled        已取消
```

关键点：

- `review_ready` 和 `submitted` 必须分开
- 默认任务应该停在 `review_ready`
- 自动点击最终提交必须有单独权限、策略和审计

## 并发策略

上百并发不能简单理解为“开上百个浏览器一起跑”。

建议做分层并发控制：

- 全局并发数
- 单平台并发数
- 单账号并发数
- 单支付卡并发数
- 单收货地址并发数
- 单网络出口并发数
- 单 worker 并发数

并发策略还需要：

- 排队
- 限速
- 失败退避
- 重试上限
- 任务超时
- 高失败率自动降速
- blocked/manual 状态过多时自动暂停

SQLite 不适合上百并发。生产建议切 PostgreSQL。

## 网络出口和代理

可以做的：

- 固定出口
- 分区域出口
- 客户组出口隔离
- 出口健康检查
- 出口故障切换
- 出口容量限制
- 记录每个任务使用的出口

不建议做的：

- 高频轮换 IP
- 用代理池规避平台封禁
- 指纹伪装
- 绕验证码
- 绕反欺诈
- 把代理作为核心成功率来源

更稳的方式：

- 每个账号或客户组绑定相对固定的出口
- 控制下单频率
- 监控失败率
- 必要时和平台沟通企业采购、白名单或合作通道

## SKU 选项管理

SKU 选项必须支持人工修订。

原因：

- 电商页面字段经常变化
- Apple 这类页面的 URL path、part number、颜色值、运营商值可能变
- 固定下拉会导致运营无法及时修复

推荐字段：

- 商品名称
- model path
- storage
- color
- carrier
- part number
- AppleCare 选项
- payment option
- option_config JSON

UI 设计：

- 常用值提供候选
- 字段允许人工输入
- `option_config` 提供 JSON 编辑区
- 运营可以根据页面变化修订配置

## Apple Checkout 自动化经验

这次 Apple 下单验证中确认的关键经验：

- `window.acStore.addItem(partNumber)` 是目前更可靠的加入购物袋方式
- 直接提交表单或直接请求 bag API 可能遇到 CSRF、404 或 541
- AppleCare 需要显式选择
- 不买 AppleCare 时要选择 `No AppleCare coverage`
- 多次重试会导致购物袋数量累加，需要进 bag 后把数量归一到 1
- ZIP 输入框可能存在于 DOM 里但不可见
- 控件存在不代表可以 fill，要判断 visible
- `Continue with other payment options` 可能是 link、button 或普通可点击文本
- 点击该控件前需要显式等待文本可见
- Shipping 表单加载可能超过 15 秒，建议至少 45 秒
- 收货表单字段 ID 当前可用，但仍要准备 fallback selector
- 支付卡无效时 Apple 会拒绝，任务应失败并记录原因
- 自动化必须停在最终提交前，除非任务策略明确允许提交

当前已验证流程：

```text
连接浏览器
打开商品页
选择 AppleCare
加入购物袋
打开购物袋
进入结账
配送信息
收货信息
支付信息
继续到确认订单
```

当前最终阻塞点：

- Apple 拒绝提供的卡号，提示卡号无效
- 没有点击最终下单

## 审计要求

生产系统必须记录：

- 谁创建/修改/删除 SKU
- 谁创建/修改/删除人工信息
- 谁创建/修改/删除任务
- 谁启动任务
- 哪个 worker 执行任务
- 使用哪个浏览器 profile
- 使用哪个网络出口
- 任务每个阶段的时间
- 是否读取支付敏感信息
- 是否进入最终确认页
- 是否点击最终提交
- 是否人工接管

日志必须避免：

- 完整卡号
- CVV
- 完整敏感证件
- 明文支付信息
- 未脱敏浏览器 trace
- 包含卡号的截图

## 生产化路线

建议按阶段推进：

1. 抽象数据库访问层，为 PostgreSQL 做准备
2. 从 SQLite 切换到 PostgreSQL
3. 引入 Redis 和任务队列
4. 拆分 worker 进程
5. 引入支付 vault/token 方案
6. 增加 RBAC 权限系统
7. 增加审计日志
8. 增加平台账号管理
9. 增加网络出口管理
10. 增加并发和限速策略
11. 增加人工接管流程
12. 增加失败分类和重试策略
13. 增加敏感字段脱敏截图/DOM 摘要
14. 增加监控、告警和运维后台

## 结论

APAgent 可以做成面向代购商的高并发自动下单系统，但生产架构不能只依赖网页脚本和代理池。

正确方向是：

- 支付信息安全
- 权限隔离
- 全链路审计
- 队列化 worker
- 可控并发
- 稳定网络出口
- SKU 选项可人工修订
- 任务可人工接管
- 默认停在最终确认前

这样才能在效率、资金安全和长期稳定性之间取得平衡。
